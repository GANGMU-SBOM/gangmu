# Limits

Binary analysis is limited, not a full disassembler or decompiler. Prebuilt libraries and firmware images (`.a`, `.lib`, `.so`, `.elf`, `.axf`, `.bin`, `.exe`, `.dll`) are inventoried, unwrapped (HEX, S-record, UF2, U-Boot uImage, gzip/xz/bzip2/zlib/zip) and read for version banners (built in, or supplied by a rule with `identity.binary_banners`), exported symbols, the ELF `.note.package`, the GNU build-id and, for shared libraries whose file name carries the release (`libz.so.1.3.1`, agreeing with the SONAME), that release at lower confidence. With the optional Capstone dependency (`pip install 'gangmu-sbom[disasm]'`) gangmu also recovers function boundaries (ELF and raw Cortex-M images, whose vector table need not be at offset 0 and may sit behind an MCUboot header; Thumb, Arm, AArch64, RISC-V, MIPS32, x86; Xtensa through a small built-in decoder; PE and Mach-O through `rules binary-prints` and `binary-eval`; `gangmu scan` matches functions in `.exe` and `.dll` only when a rule carries references built for that CPU, and twelve free rules carry x86-64 fingerprints (zlib, littlefs, Mbed TLS, Lua, zstd, bzip2, libdeflate, expat, libpng, Brotli, yyjson, PCRE2), so PE files of other libraries are not matched by function yet; on Ubuntu's own builds the version ranges contain the true release but coverage is 37% to 100% (BINARY-VALIDATION, last section)) and matches per-function fingerprints (`identity.binary_functions`). Everything here is lower-confidence supporting evidence. Measured limits (docs/BINARY-VALIDATION.md): most Linux distribution libraries carry no banner; fingerprints exist for only a few rules; firmware built by a compiler other than the references' is recognised as the library with a release range; a match from another architecture names the library and the whole recorded range; real firmware gives much wider ranges than the self-built benchmark. This English page is a summary: the Chinese [LIMITS.md](LIMITS.md) has the figures. Windows `.exe` and `.dll` files are also read for the PE import and export tables and version resource, the dependency lists the Go and Rust (`cargo auditable`) toolchains write into the file, .NET assembly references and the `*.deps.json` beside a program; see [BINARY-SBOM.md](BINARY-SBOM.md) for what each proves, what is not done and how it was checked. A statically linked C/C++ program with no banner is still not recognised. Benchmarks now span a dozen-odd component families (about a hundred real upstream trees and several dozen copies inside Chinese vendor SDKs, see docs/BENCHMARK.md), not a corpus of thousands.
Rule coverage is still small; Allwinner Tina Linux SDKs (the RTOS SDKs are covered) are not
in Zephyr and need their own import. Recursive import
(`gangmu rules import --recursive`) covers `.gitmodules` SDKs and west manifests; for west it
follows the common `import:` forms (true, file/directory paths, allow/block lists, `path-prefix`,
and lists of these) to depth 4, but not `import-flags` or imports via west extension commands.
`gangmu vuln` itself never touches the network; `gangmu vuln-fetch` is the
separate online step that fills its directory (`--sbom` for just the products an
SBOM can match, `--all` for the whole NVD, incremental afterwards). The compiler
wrapper works on POSIX and Windows, but it only intercepts compilers the build finds
by name on `PATH`: `make` with an absolute `CC=/opt/gcc/bin/gcc` bypasses it. On
Windows the shim is a real `gcc.exe` built from pip's vendored distlib launcher, so
`cmd /c` and plain `mingw32-make` recipes are recorded, and so is MSVC `cl.exe`
(`/c`, `/Fo`); a cross compiler, `arm-none-eabi-gcc`, works too (all verified in CI on
windows-latest with MinGW gcc, clang, MSVC and the Arm GNU toolchain from Chocolatey). Without that launcher it falls back to a `.cmd` file
that only `cmd.exe` finds, and builds run under MSYS/Git `sh` are not verified.
`gangmu wrap` warns when nothing was recorded; use `--project` then.

Linux distribution libraries are only partly identified: version banners cover few libraries (4 of 13 on Ubuntu 24.04) and distributions often strip them; `.note.package` helps only where the distribution wrote it. On clang-built Thumb firmware function-boundary recall and precision are both about 0.98 (a tail-called leaf, `crc32_z`, is missed), and a controlled comparison against gcc-built references (docs/BINARY-VALIDATION.md) found the library in clang builds of zlib and Mbed TLS (26-33% coverage) but not littlefs, with a release range rather than a single release. High-entropy raw images get a note; the scan does not decrypt or unpack them.
