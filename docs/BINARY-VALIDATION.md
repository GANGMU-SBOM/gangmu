# 二进制识别的验证：准确率、召回率与误报

没有源码、只有编译好的库或固件镜像时，纲目用逐函数指纹认库和版本：从机器码里还原每个函数引用的字符串和显著常量，与规则自带的参考指纹比对（`identity.binary_functions`，由 `gangmu rules binary-prints` 生成）。这一页是这套方法在交叉编译基准上的结果，全部可以用仓库里的工具复现。数字是 2026-10-31 用当前代码测的。

## 方法

- **语料**（`benchmarks/binary/build_corpus.py`，库的清单在 `benchmarks/binary/libs.yaml`）：14 个库、15 组构建，每个库若干个发布版，每个版本用 `-Os -O2 -O1 -O0` 四个优化级别编译，链接成 ELF 再 `strip -s`。库是 zlib、cJSON、littlefs、lz4、inih、heatshrink、Mbed TLS（只有密码学部分的 `mbedtls`，和再加 TLS 与 X.509 层的 `mbedtls-full`）、Lua、zstd、bzip2、libdeflate、Brotli、yyjson、PCRE2；AArch64 上还有 libpng。expat 和其他架构上的 libpng 在这些交叉编译器下没有编出来，不在结果里。**只链接库自己的代码，不带 libc 和 libgcc**：参考指纹里混进 libc 的 `printf`、`malloc`，认出来的就是 libc 而不是库。**不带 `assert()`**：assert 的字符串会让参考指纹在作者自己的构建上虚高，出货的固件一般不带。
- **四种架构**：Cortex-M3（`arm-none-eabi-gcc 13.2.1 -mcpu=cortex-m3 -mthumb`）、rv32imac（`riscv64-unknown-elf-gcc`）、AArch64（`aarch64-linux-gnu-gcc 13.3.0`）、Xtensa ESP32（乐鑫的 `xtensa-esp32-elf-gcc 13.2.0`）。
- **评测**（`gangmu binary-eval --corpus DIR`）：对每个库，用一个优化级别的构建做参考指纹，去识别所有优化级别、所有版本的剥离符号的镜像。每个单元格是一个镜像，结果是四种之一：`exact`（版本唯一且正确）、`range`（`低~高` 区间，含真实版本）、`wrong`（认出了这个库，但版本或区间不含真值）、`none`（没认出这个库）。
- **负对照**：把每个库的参考指纹拿去匹配其他每个库的每个镜像，任何匹配都是误报。同一个库的两种构建（`mbedtls` 与 `mbedtls-full`）不互为负对照。
- **共有函数**：几个库共有的函数（lz4 和 zstd 都带着 xxHash）对哪个库都不算证据。评测和扫描用同一套做法（`fprint.segment_prints`）：每个库的参考指纹与其他库所有优化级别的参考指纹比较，共有的函数从两边都去掉；只有一个库几乎整个都在另一个库里时，它是被打包进去的那个，保留自己的函数，由宿主让出。`--no-segment` 关掉这一步。
- **特征**：函数引用的字符串、用到的显著常量，以及引用的只读数据表开头 16 字节（CRC 表、霍夫曼表这类，与链接时放在哪里无关；全零、短字符串和由指针组成的表不算）。Xtensa 没有 Capstone 解码器，由自带的 `xtensa.py` 按指令长度走一遍，跳过跳转和返回后面的填充字节。
- **哪个版本投票**：一个镜像函数同时装得下某个函数几个版本的指纹时（旧版本的指纹小，常常被新版本长大的函数「包含」），只有和它最像的那一个参与判断版本（`fprint._best_fits`）；都还算作认出了这个库。不同函数的指纹，比如内联进来的被调函数，各自都算。
- **怎么算匹配上**：参考函数至少 70% 的特征都在镜像的某个函数里。镜像这边除了每个函数本身，还看「函数加上它直接调用的函数」（不超过 16 个被调函数）：同一段代码在 `-O2` 下常被内联成一个函数，在 `-O0` 下分在两个函数里，参考指纹和镜像的优化级别不同时，只有合起来才对得上（N2NMatcher 的观察，见下文「方法来源」）。只在合起来时才匹配上的参考函数，只给已经有至少 3 个函数单独匹配上的库加分，而且不参与判断版本：被调函数可能是别的版本的，大一点的并集也会碰巧装下别的库的小指纹（LibAM 的做法：先有锚点，再看邻居）。镜像里比参考函数大 32 倍以上的函数不算：错误码 switch、常量表里有几百个值，碰巧装得下别的库的小指纹。
- **什么时候报出一个库**：至少 5 个函数匹配上、且占这个版本可匹配函数的 12% 以上；或者至少 3 个函数、占一半以上（只有三四个可匹配函数的小库，例如 cJSON，原来永远到不了 5 个）。
- **跨架构**（`--images` 另一种架构的语料）：参考指纹和镜像不是同一种 CPU 时只比字符串，编译器生成的常量在不同架构之间不一样。这时只报库，版本给规则覆盖的整个区间。

### 指标

| 指标 | 定义 |
| --- | --- |
| 召回率 | 认出了库的镜像（exact + range + wrong）/ 全部镜像 |
| 精确率 | 认对的库（上面那些）/（认对的库 + 负对照里的误报） |
| 版本完全正确 | exact / 认出了库的镜像 |
| 版本正确或区间含真值 | (exact + range) / 认出了库的镜像 |
| 负对照命中率 | 负对照误报 / 负对照对数 |

## 结果

同一种架构（参考指纹和镜像是同一种 CPU，比较字符串和常量）：

| 架构 | exact | range | wrong | none | 召回率 | 精确率 | 版本完全正确 | 版本正确或区间含真值 | 负对照命中 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Cortex-M3 | 303 | 255 | 8 | 122 | 82.3% | 100% | 53.5% | 98.6% | 0 / 9,776 |
| rv32imac | 286 | 244 | 1 | 157 | 77.2% | 100% | 53.9% | 99.8% | 0 / 9,776 |
| AArch64 | 339 | 259 | 4 | 134 | 81.8% | 100% | 56.3% | 99.3% | 0 / 11,200 |
| Xtensa | 318 | 205 | 0 | 123 | 81.0% | 100% | 60.8% | 100% | 0 / 9,118 |

跨架构（只比字符串）：

| 参考 → 镜像 | exact | range | wrong | none | 召回率 | 精确率 | 版本正确或区间含真值 | 负对照命中 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Cortex-M3 → rv32imac | 118 | 107 | 6 | 457 | 33.6% | 100% | 97.4% | 0 / 9,776 |
| Cortex-M3 → AArch64 | 117 | 119 | 0 | 452 | 34.3% | 100% | 100% | 0 / 10,496 |
| Cortex-M3 → Xtensa | 126 | 96 | 2 | 440 | 33.7% | 100% | 99.1% | 0 / 9,440 |
| Xtensa → Cortex-M3 | 116 | 96 | 0 | 452 | 31.9% | 100% | 100% | 0 / 9,448 |

怎么读：

- **认出的库都对**：四种架构上精确率都是 100%，约 4 万对负对照一次也没命中。
- **版本一半以上能唯一定下**：唯一定到一个版本的 54% 到 61%，区间含真值的比例在 98.6% 以上，报错版本的共 13 个（AArch64 4 个、Cortex-M3 8 个、rv32imac 1 个、Xtensa 0 个）。其余是区间：相邻版本改动的函数少，指纹能分辨的就少；`-O0` 构建的参考指纹去认 `-Os`/`-O2` 的镜像时尤其如此。
- **认不出的镜像大半是两个库**：inih 和 heatshrink 每个版本只有一个函数引用了字符串或显著常量（各架构 80 个认不出的镜像都是它们），这种特征下无从识别；要认它们需要指令级的特征。其余认不出的主要是 cJSON 和 `-O0` 镜像。
- **跨架构召回率 32% 到 34%**，因为只剩字符串可比；认出的仍然都对。扫描时跨架构只报库，版本给规则覆盖的整个区间，所以上表里的版本一栏只说明字符串本身能分辨多少。

与只比每个函数本身、只用 5 个函数这一道门槛、不排除大函数、所有包含了的指纹都参与判断版本时相比（同一语料）：同架构召回率 Cortex-M3 78.2% → 82.3%，rv32imac 76.6% → 77.2%，AArch64 81.2% → 81.8%，Xtensa 72.3% → 81.0%；唯一定到一个版本的 Cortex-M3 43.3% → 53.5%，rv32imac 37.6% → 53.9%，AArch64 42.5% → 56.3%，Xtensa 46.5% → 60.8%；报错版本的共 30 → 13 个；负对照命中 29 → 0。几处改动的贡献：
- **同一函数只让最像的版本投票**：语料上的区间大多来自这种成对的互相矛盾。只改这一处，跨优化级别比较时唯一定到一个版本的从 34.8% 升到 48.5%，报错版本的从 1.6% 降到 0.8%，召回率不变。把容忍度 `CONTRA_SPAN` 从 2 收紧到 1 也能把唯一定到的比例提到 45.6%，但报错版本的会涨到 4.1%，所以没有这么做。
- **Xtensa 的指令遍历**：跳转、返回后面的填充字节原来被当成指令，后面的指令就错位了；对照 objdump，zstd `-Os` 里找到的 `l32r` 有三成并不存在、真的漏了 84 条，这些错位读出的常量每次构建都不一样。修正后 Xtensa 召回率 76.9% → 81.0%。
- **大函数里不算匹配**（`MAGNET_RATIO` 16）：去掉了最后 2 次负对照命中（Cortex-M3 上 Brotli 的指纹落在 yyjson `-O0` 的大函数里）。
- **闭包只扩展已有锚点的库**：闭包曾经也参与判断版本（0.16.0），AArch64 上报错版本的有 27 个。

此前这一页的跨架构数字（36% 到 60%）偏高：评测的特征缓存没有保留哪些特征是字符串，跨架构时连常量一起比了，而扫描只比字符串。缓存修正后才是上表的 32% 到 34%。真实文件（PyPI、NuGet 包里的二进制，整棵 ESP-IDF v5.4.2）的扫描结果前后相同。

### 方法来源

- **内联**：N2NMatcher（Jia 等，arXiv:2608.10043，2026）说明不同优化级别的内联决定会同时改变调用图的结构和函数本身的内容，一个二进制函数可能对应另一份构建里的几个函数。这里不用它的图神经网络，只取最便宜的那一步：镜像里一个函数和它直接调用的函数合起来比较。
- **锚点**：LibAM（Li 等，arXiv:2305.04026）指出给整个二进制设一个阈值会漏掉小规模的复用，先找强匹配的函数作锚点再看调用图上的邻居。这里对应的是小库的门槛：3 个函数、占一半以上。
- **同一函数只让最像的版本投票**：BinCoFer（Zou 等，arXiv:2504.19551）也只让每个目标函数取它最像的那个库函数；这里把它限定在同一函数的几个版本之间，内联进来的其他函数照样计数。
- 同类工作（LibDB、ModX、BinCoFer、BinaryAI）用神经网络把函数编码成向量，需要 GPU；这里的方法只用字符串和常量，不需要。

## 免费规则库里的固件指纹

上面的评测用语料自己的参考指纹；扫描真实固件时用的是规则库里的。免费规则库带的固件 CPU 指纹：Thumb（Cortex-M）7 个库、RISC-V 9 个、Xtensa（ESP32）7 个、AArch64 11 个（库名见 [LIMITS.md](LIMITS.md)）。每份都用该库规则覆盖的各个发布版、各两种构建（`-Os`、`-O2`）生成，并通过了 `gangmu rules binary-prints` 的自检：没有认错版本、没有漏认跨构建的镜像、负对照（同一 CPU 上其他所有库，包括没有指纹的 lz4、cJSON、inih、heatshrink）一次也没命中。没通过的不收进规则库。

用整个免费规则库扫上面语料里的剥离镜像（4 个优化级别，大多不是生成指纹用的那两种构建），按函数认出的镜像数，加入这批指纹前 → 后：Cortex-M3 32 → 56（176 个镜像），rv32imac 30 → 66（176），Xtensa 17 → 38（170，Xtensa 指纹用修正后的指令遍历重建之后），AArch64 22 → 78（188），认成别的库的次数前后都是 0。Lua、zlib、Mbed TLS 的镜像本来就靠版本横幅认出，横幅被去掉时才用到函数指纹。新认出的里面，有 3 个镜像把指纹记录过的版本报错了（PCRE2 10.37、10.40 的 `-O0` 报成 `10.42~10.44`，yyjson 0.10.0 的 `-Os` 报成 0.7.0）；指纹没记录的版本（littlefs 2.4.0、2.5.0）报成最近的记录区间。

## 真实源码树里的预编译文件

227 条规则钉定的上游发布版（源码树）里，扫描认出了 15 个预编译文件：premake4 里的 Lua 5.1.4、premake5 里的 libcurl 7.53.1、几个 DLL 里静态链接的 zlib（1.3.1、1.2.3）、libogg、libopus 1.4，以及 TF-M 安全镜像里的 Mbed TLS。**15 个都是真的**；版本多半只有区间或没有。

## 这一轮没有测的

下面这些能力都在，但这一轮没有在当前版本上重新测，所以这里不给数字：

- 真实厂商固件（例如 Zephyr 自己的构建）。参考构建和真实固件的配置不同（配置宏、是否带 assert）时，匹配上的函数会明显变少，版本区间更宽。
- clang 编译的镜像对 gcc 编译的参考指纹。
- Windows PE（含 Windows CE）、Mach-O、MIPS32 的函数指纹，以及 Linux 发行版里的库（Ubuntu 的包、OpenWrt 的包）。

## 复现

```
python benchmarks/binary/build_corpus.py --out /tmp/corpus --target arm   # 也可以 riscv32、aarch64、xtensa
gangmu binary-eval --corpus /tmp/corpus                                      # 需要 pip install 'gangmu-sbom[disasm]'
gangmu binary-eval --corpus /tmp/corpus-arm --images /tmp/corpus-riscv32     # 跨架构
```

需要 git、网络和对应的交叉编译器。构建 Mbed TLS 最慢；`--lib` 可以只建一部分库，`--relink` 复用上次编译的目标文件。
