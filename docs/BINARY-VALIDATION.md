# 在真实 ARM、RISC-V 和 AArch64 固件上验证二进制识别

前几档（函数边界恢复、逐函数指纹）最初只用 x86-64 的 gcc 产物和手工编码的指令验证。这份文档记录在
**真实 Cortex-M3 固件**上的结果，包括没做成的、以及后来发现之前数字不对的部分。

## 方法

- **语料**（`benchmarks/binary/`，`build_corpus.py` 一键构建）：7 个库、20 个发布版本，每个版本用
  `arm-none-eabi-gcc 13.2.1 -mcpu=cortex-m3 -mthumb` 编 `-Os -O2 -O1 -O0` 四个优化级别，链接成带向量表的
  ELF，再 `strip -s`。库是 zlib、cJSON、littlefs、lz4、inih、heatshrink、mbedtls（3 个版本各一）。
  **库代码单独链接，不带 libc 和 libgcc**：参考库只能含库自己的代码，见下面的「纠正」。
- **评测**（`gangmu binary-eval --corpus DIR [--loo]`）：对每个库，用一个优化级别的构建做参考指纹，去识别另一个
  优化级别的、剥离了符号的镜像，所以参考库从没见过它要识别的那个镜像。每个单元格的结果是四种之一：
  `exact`（版本唯一且正确）、`range`（给出 `低~高` 区间，且区间包含真实版本）、`wrong`（给出的版本或区间不含
  真实版本）、`none`（没认出这个库）。负对照：把一个库的指纹拿去匹配另一个库的镜像，任何匹配都是误报。
- 一切都在同一台机器、同一个编译器、同一种架构上，样本是 7 个库，**这是一次实测，不是统计结论**。

## 纠正：之前的识别率数字作废

这个 PR 最初的版本只用 zlib 和 cJSON 验证，参考构建把 newlib 的 `printf`、`strtod`、`malloc` 一起链了进去。
这些共用的 libc 函数成了「库的指纹」：cJSON 看起来能被认出来，其实认出来的是 libc；cJSON 和 mbedtls 之间
还出现了 96 对错误匹配。去掉 libc 重新构建后，cJSON 在 48 个单元格里 42 个认不出来（它只有 7 个
有指纹的函数，达不到「至少 5 个函数匹配才认定这个库」），误报归零。zlib 的数字也受影响。
**以下取代之前所有关于识别率的数字。**

## 逐函数指纹的识别率（默认阈值：最少 2 个特征，并列阈值 0.85）

> 这一节是当时的结果，用的是并列阈值 0.85 评分。2026-10 起默认评分改为按矛盾证据计（见本文「版本评分改为按「矛盾证据」计」一节），`--tie-share 0.85` 可复现本节的数字。

320 个单元格（7 个库 × 参考优化级别 × 镜像优化级别 × 版本）：

| | exact | range | wrong | none |
|---|---|---|---|---|
| 全部 | 88 | 98 | **5** | 129 |
| 同一优化级别 | 39 | 15 | 0 | 26 |
| 不同优化级别 | 49 | 83 | 5 | 103 |
| 参考和镜像都不含 `-O0` | 52 | 61 | 1 | 66 |

- **负对照：1920 对，0 次误报。**
- **给出了答案的 191 个里 5 个是错的（2.6%）**，全是 lz4：4 个是 `-O0` 构建的参考库去识别 `-Os`/`-O2`
  的镜像，1 个是 `-O2` 参考识别 `-Os` 镜像。不含 `-O0` 时 114 个答案里 1 个错。
  错误答案的覆盖率（0.47–0.70）和正确答案（0.18–1.0）重叠，没有一个简单的覆盖率阈值能把它们筛出来。
- **「没认出」多半是构造性的**：库里有指纹的函数（至少 2 个字符串或常量）太少，达不到 5 个。
  inih 和 heatshrink 各只有 1 个，cJSON 7 个，zlib 11 个，lz4 27 个，littlefs 43 个，mbedtls 141 个。
  没有字符串或显著常量的小库，这个方法认不出来。
- 相邻版本几乎总是并列，所以多数答案是区间；littlefs 的版本差别大，能唯一识别。

### 两个阈值怎么选，以及它们泛化到什么程度

整张表随阈值变化（全部 320 个单元格，负对照每个都是 0 次误报）：

| 最少特征 | 并列阈值 | exact | range | wrong | none |
|---|---|---|---|---|---|
| 2 | 0.95 | 122 | 55 | 14 | 129 |
| 2 | 0.90 | 101 | 80 | 10 | 129 |
| 2 | **0.85（当时的默认）** | 88 | 98 | 5 | 129 |
| 2 | 0.80 | 82 | 105 | 4 | 129 |
| 3 | 0.85 | 80 | 90 | 7 | 143 |
| 3 | 0.80 | 75 | 98 | 4 | 143 |

- 方向是单调的：并列阈值越低，错误越少、唯一识别越少；最少特征取 2 比 3 好。这个趋势在原先只用 2 个库
  调参时就有，现在在 7 个库上仍然成立，说明方向不是过拟合 zlib 和 cJSON 的产物。
- **留一库验证**（`--loo`）：每次拿掉一个库，在其余库上选阈值，再测被拿掉的那个。每一折选出的都是
  最少 2 个特征、阈值 0.8 或 0.85，没有一折选 3；合起来：83 exact / 103 range / 5 wrong / 129 none，
  0 次误报，和用全部数据选出来的默认值几乎一样。
- **但这不是泛化保证**：网格只有 8 个点，7 个库、一个编译器版本、一种架构、相近的编译选项，每个库
  只有 3 个版本。它能说明「调出来的阈值没有明显过拟合这批库」，说明不了没见过的编译器、架构或库。
  并列阈值再往下降，错误数的下降已经很小（5 → 4），不值得再调。

## 函数边界（7 个库，剥离符号的 ELF，对照同一构建的符号表）

| | 召回 | 精确率 |
|---|---|---|
| 全部（15329 个函数） | **0.85** | **0.84** |
| `-Os` / `-O2` / `-O1` / `-O0` | 0.81 / 0.72 / 0.88 / 0.96 | 0.91 / 0.88 / 0.93 / 0.73 |
| 各库 | 0.72（cJSON）～ 0.93（littlefs） | 0.62（heatshrink）～ 0.93（littlefs） |

这比最初在 zlib 上看到的 0.96 / 0.89 低不少：那个数字是在 zlib 一个库上调出来的，并且构建里带了 libc。
`-O2` 最差。真实代码在最初暴露了四个问题，都已修：

1. **字面量池**让线性扫描整体错开半个字 → 先收集可靠的起点，再从每个起点重新解码。
2. **提前排布的加载**：gcc 常把 `ldr` 排在 `push` 之前，函数起点比 `push` 早 2–8 字节 → 已知起点之后、
   第一个返回之前的 `push` 算同一个函数。
3. **常量表被当成代码**：CRC 表、字符串池里有看起来像 `push {…, lr}` 的字 → 代码范围限制在最后一个
   被调用或被指向的函数之后 0x400 字节内。
4. **函数指针表**：只被表引用的叶子函数既没有调用者也没有 lr → 连续三个以上的代码指针算函数表。
   `tests/test_thumb_firmware.py`（需要 `arm-none-eabi-gcc`，没有就跳过）固定了这一条。

没找到的是只被尾调用（`b.w`）到、没有 `push` 的叶子函数。

## 没做成的：跨架构参考库

> 后来在新语料上重测，改成只比字符串后做成了，见「2026-10-08：跨架构」一节；下面是最初的失败记录。

原先的设想是在 x86-64 主机上编译上游各版本做参考库，再匹配 Thumb 固件。**真实数据不支持**：x86-64 `-O1`
参考库对 Thumb 镜像，zlib 和 cJSON 的 6 个单元格全部没有匹配。编译器会**派生**常量（对 65521 取模编成
倒数乘数，`"true"` 四个字符合成一个 32 位存储，64 位掩码在 Thumb 上变成别的常量），结构体偏移也因指针
宽度不同而不同。参考库要为固件的架构编译，最好工具链族也一致。这一条是在最初的两个库上测的，
**没有在新语料上重测**。

## RISC-V（rv32imac）

同一套方法换成 `riscv64-unknown-elf-gcc -march=rv32imac -mabi=ilp32`（`build_corpus.py --target riscv32`），
同样的 7 个库、20 个版本、4 个优化级别，链接脚本把 `.rodata` 放在独立的节里（常见的 MCU 链接脚本都这样）。
这是第二种架构，不是第二个编译器：编译器仍是 gcc 13，选项相近。

### 函数边界（剥离符号的 ELF，对照符号表，15345 个函数）

| | 召回 | 精确率 |
|---|---|---|
| 最初（只按调用目标和 `addi sp, sp, -N` 序言） | 0.37 | 0.94 |
| 补上 `c.jal`、叶子函数的「闭合」规则 | 0.99 | 0.88 |
| 再加上近距离前向跳转、跳过落在分支目标上的序言（AArch64 一节里说明） | **0.99** | **0.94** |
| `-Os` / `-O2` / `-O1` / `-O0` | 0.98 / 0.97 / 0.99 / 1.00 | 0.97 / 0.90 / 0.95 / 0.94 |
| 各库 | 0.97（littlefs）～ 1.00 | 0.71（inih）～ 0.96 |

规则是在 zlib 和 cJSON 上调的；另外 5 个库没参与调参，召回/精确率是 0.99/0.94，调参用的两个库是 1.00/0.95，
没有看到过拟合。真实代码暴露了三个问题，都已修，`tests/test_riscv_firmware.py`（需要
`riscv64-unknown-elf-gcc`，没有就跳过）固定了这几条：

1. **`c.jal`**：RV32C 里，链接器把近距离的调用缩成两字节的 `c.jal`，原来的调用目标解码只认四字节的
   `jal`，大半调用都没看到（召回 0.37 → 0.46）。
2. **叶子函数没有序言**：库的导出函数大多没有被调用，也不一定以 `addi sp, sp, -N` 开头。现在从编码
   里解出分支：一个函数以 `ret` 或无条件 `j` 结束，且之前没有条件分支跳到它后面，下一条指令就是新函数
   的开始（召回 0.46 → 0.99，精确率掉到 0.48）。
3. **边界条件写错了**：「有分支跳到下一条指令」也算函数没结束，我写成了「跳到下一条之后」，把提前返回的
   分支块切成了新函数（精确率 0.48 → 0.88）。

**裸 `.bin`（没有节表）**：召回仍是 0.99，但精确率只有 0.39–0.97，常量表多的库（zlib、littlefs）
只有 0.4–0.5，因为表里的字被当成代码。给出代码大小（`gangmu binary-functions --code-size`）才能避免。
ARM 的 Cortex-M `.bin` 靠向量表和「代码范围」启发式处理了这个问题，RISC-V 没有。

这个闭合规则没有用在 Thumb 上：Thumb 的字面量池会被当成新函数，需要另外处理。

### 逐函数指纹的识别率（默认阈值）

| | exact | range | wrong | none |
|---|---|---|---|---|
| RISC-V（320 个单元格） | 72 | 124 | **7** | 117 |
| ARM（对照，上面的表） | 88 | 98 | 5 | 129 |

- **负对照：1920 对，0 次误报**，但这是调了一个参数以后的结果：最低覆盖率 0.08 时 RISC-V 上有 1 次
  误报（littlefs 的指纹匹配到 mbedtls 的镜像，7 个函数、覆盖率 0.104），把下限提到 0.12 后这次误报没了，
  代价是 125 个答案里少了 1 个。这是看到一次误报之后调的，ARM 上没有区别。
- 给出了答案的 203 个里 7 个错（3.4%）：cJSON 2、zlib 2、lz4 3。不含 `-O0` 时 180 个单元格里 3 个错。
- **留一库验证：** 被拿掉的库合起来 68 exact / 111 range / 4 wrong / 137 none，0 次误报。
- **两种架构选出的阈值不一样**：ARM 每一折都选「最少 2 个特征」，RISC-V 大多数折选 3（3 个特征时
  `none` 从 117 涨到 146，错误从 7 降到 3）。默认值是 2，所以这是两种架构的阈值并不通用的证据，不是
  已经解决的问题。要不要按架构区分默认值，还没有足够的数据来定。
- 有指纹的函数（最后一个版本、`-Os`、至少 2 个特征）：zlib 14、cJSON 4、inih 0、heatshrink 0、mbedtls 183、
  lz4 45、littlefs 41；ARM 上对应是 11、7、1、1、141、27、43。

**没有验证的**：RISC-V 上用 x86-64 或 ARM 参考库去匹配（跨架构）；64 位 RISC-V；非 gcc 编译器；
真实厂商 SDK 编出来的固件（带中断向量表、启动代码、各种库混在一起）。AArch64 已有（见上），Xtensa 见下一节。

## AArch64

同一套方法，`aarch64-linux-gnu-gcc -march=armv8-a -ffreestanding`（`build_corpus.py --target aarch64`），
静态链接、不带 libc，同样的 7 个库、20 个版本、4 个优化级别。**这是 Linux 目标的编译器用在无操作系统
的固件上**（Ubuntu 没有 `aarch64-none-elf`），`-ffreestanding -nostdlib` 去掉了对 libc 的依赖，但不是
真正的裸机工具链，选项和默认值可能和厂商的不一样。

### 函数边界（剥离符号的 ELF，对照符号表，15413 个函数）

| | 召回 | 精确率 |
|---|---|---|
| 不做任何 AArch64 专门处理（只按调用目标和 `stp`/`sub sp` 序言） | 0.78（zlib `-Os`） | 0.80 |
| 加上从编码解出的分支和闭合规则 | 1.00 | 0.69（zlib） |
| 再加上近距离前向跳转、跳过落在分支目标上的序言、把 `udf` 当对齐填充 | **1.00** | **0.94** |
| `-Os` / `-O2` / `-O1` / `-O0` | 1.00 全部 | 0.96 / 0.89 / 0.96 / 0.95 |
| 各库 | 0.99–1.00 | 0.65（inih）～ 0.95（mbedtls） |

后两步是在 zlib 上看出来的，另外 6 个库的结果和 zlib 一样（1.00/0.94），没有过拟合的迹象。这两步也用到了
RISC-V 上（精确率 0.88 → 0.94）：

- **旋转的循环**：gcc 把循环写成「跳到判断处，循环体在跳转之后」，循环体只被后面的回跳分支到达，原来的
  闭合规则看不到，就把循环体当成新函数。现在一个距离不超过 512 字节的前向无条件跳转也算函数在这之后
  继续。
- **一个假的开头引起连锁反应**：序言规则在函数中间误认了一个起点，之后把「已知分支目标」清零，后面又连着
  误认。现在如果有分支落在这条指令上或之后，就不接受它做起点。

`udf #0`（全零字）是 gcc 的对齐填充，不能算新函数的第一条指令。

### 逐函数指纹的识别率（默认阈值）

AArch64 的 `adrp` + `add`（地址）、`movz` + `movk`（常量）也折回源码里的值（和 x86-64、Thumb、RISC-V 上同一个
函数的指纹一致，有测试）。

| | exact | range | wrong | none |
|---|---|---|---|---|
| AArch64（320 个单元格） | 89 | 106 | **4** | 121 |
| RISC-V | 72 | 124 | 7 | 117 |
| ARM | 88 | 98 | 5 | 129 |

- **负对照：1920 对，0 次误报。**
- 给出了答案的 199 个里 4 个错（2.0%），全是 lz4，全是 `-O0` 构建的参考库；参考和镜像都不含 `-O0` 时
  115 个答案里 0 个错。
- **留一库验证：** 被拿掉的库合起来 83 exact / 112 range / 4 wrong / 121 none，0 次误报；每一折选出的都是
  最少 2 个特征，和 ARM 一致，和 RISC-V 不一致（RISC-V 大多数折选 3）。所以最少特征数在 ARM 和 AArch64
  上是 2，在 RISC-V 上是 3：三种架构里有两种一致，不是通用的结论。
- 有指纹的函数（最后一个版本、`-Os`、至少 2 个特征）：zlib 23、cJSON 7、inih 0、heatshrink 0、
  mbedtls 199、lz4 45、littlefs 49。inih 和 heatshrink 一个都没有。

**没有验证的**：AArch64 上跨架构参考库；真正的裸机 `aarch64-none-elf` 工具链；64 位 RISC-V；非 gcc 编译器；
真实厂商 SDK 的固件；带 PAC/BTI 指令（`paciasp` 等）的构建。Xtensa 只验证过一个 gcc 版本。

## 规则作者的自校验

上面是我们自己的语料。规则作者发布 `binary_functions` 时，`gangmu rules binary-prints` 会先在作者
提供的构建上做同样的检验：每个版本至少给两个构建（例如 `-Os` 和 `-O2`，写成
`--ref 1.2.11:Os=a.elf --ref 1.2.11:O2=b.elf`），一个构建做参考、其余构建剥离符号后当镜像去识别，
参考指纹从不见到它自己的镜像；`--negative` 给的无关固件必须一个都不匹配。通过的条件：至少 2 个版本、
至少 10 个有指纹的函数、跨构建没有错误版本也没有认不出来的镜像、负对照零误报。没通过就**不写文件**。
结果写进边车，并复制到规则的 `calibration` 块；加载规则时，块缺失、`passed: false`、或和边车里存的
对不上都会被拒绝，`rules lint` 也会报。扫描时证据里会写作者的自测结果。

在上面的语料上试了一遍（每个版本只用 `-Os` 和 `-O2` 两个构建，没有负对照）：

| 库 | 有指纹的函数 | 跨构建 exact / range / wrong / none | 结果 |
|---|---|---|---|
| littlefs | 195 | 5 / 1 / 0 / 0 | 通过 |
| zlib | 36 | 2 / 4 / 0 / 0 | 通过 |
| mbedtls | 236 | 1 / 5 / 0 / 0 | 通过 |
| lz4 | 52 | 0 / 5 / **1** / 0 | **拒绝**：有一个跨构建答案是错的版本 |
| cJSON | 10 | 0 / 0 / 0 / 6 | **拒绝**：6 个镜像都没认出这个库 |

被拒绝的正是上面基准里最有问题的两个库（lz4 的错误答案、cJSON 的识别不出来），作者自己的自测就能发现，
不需要我们的语料。

这能说明指纹在作者自己编的构建之间认得出这个库、没有在作者试过的固件上误报，**说明不了**在作者没试过的
编译器、选项或架构上也成立。

## 复现

```
python benchmarks/binary/build_corpus.py --out /tmp/corpus     # 需要 git、网络和 arm-none-eabi-gcc
gangmu binary-eval --corpus /tmp/corpus --loo                   # 需要 pip install 'gangmu-sbom[disasm]'
```

构建 mbedtls 最慢（约 20 分钟）；`--lib` 可以只建一部分库，`--relink` 复用上次编译的目标文件。

## 2026-10-08：栈偏移被当成"显著常量"（已修）
在 arm-none-eabi、riscv64-unknown-elf、aarch64-linux-gnu 三个交叉编译器上重建语料（zlib、cJSON、littlefs、lz4、inih、heatshrink 加 mbedtls 当负对照镜像）重跑 `binary-eval`，发现 RISC-V 在默认阈值下有 **3 次误报 / 1920 对**（littlefs 的指纹匹配到 mbedtls 的 `-O0` 镜像）。逐个看匹配上的函数，共同特征全是 `0xFFFFFFxx`：`-36`、`-28` 这类栈帧偏移和步长，在 `-O0` 里几乎每个函数都有，却被当成了"显著常量"。上面"最低覆盖率从 0.08 提到 0.12"那次调参，压掉的正是同一个问题的一个症状。

修法（`fprint.py`）：离 `2**bits` 不到 4096 的值（以及 x86-64 上 32 位 `mov` 零扩展出来的同一段）不再计作常量。修后三个架构负对照均为 0 次误报：

| 目标 | 修前 exact / range / wrong / none | 修后 |
| --- | --- | --- |
| Cortex-M3 | 74 / 63 / 6 / 129 | 75 / 62 / 6 / 129 |
| rv32imac | 70 / 128 / 3 / 119，**3 次误报** | 75 / 109 / 4 / 132，0 次误报 |
| AArch64 | 89 / 106 / 4 / 121 | 同左 |

RISC-V 少了 19 个答案（其中一部分是靠这些栈偏移撑起来的匹配），exact 多了 5 个，wrong 多了 1 个。对一个要进 SBOM 的结论，用少量召回换掉误报是值得的。

**没有放宽阈值。** 修复后 RISC-V 在 `MIN_MATCHES=2, MIN_COVERAGE=0.04` 下也是 0 次误报，但 AArch64 在同样设置下有 12 次（mbedtls 的指纹匹配到 zlib 的镜像），所以默认值（5 个函数、覆盖率 0.12）不动。语料只有 7 个库，这不是泛化的证据。

**另一个没成的想法：** 用命中函数在映像里的位置聚集度来区分真假命中（链接器把一个库的函数排在一起）。在 Cortex-M3 语料上，正确命中与错误发行版的聚集度几乎相同（中位数 0.15 对 0.15~0.22），因为库里多数函数没有指纹，窗口里本来陌生函数居多，没有区分力，已放弃。

**升级提示：** 用旧版本生成的 `.fnprint` 指纹里带着这些栈偏移特征，匹配时它们永远对不上，会让覆盖率略低；用 `gangmu rules binary-prints` 重新生成，并把规则里记录的 sha256 一并更新。

## 2026-10-08：跨架构（参考库与固件不是同一种 CPU）
`binary-eval --corpus A --images B` 现在可以把 A 的参考库去匹配 B（另一种架构）的镜像。用 Cortex-M3 的参考库、rv32imac 与 AArch64 的镜像（zlib、cJSON、littlefs、lz4、inih、heatshrink 加 mbedtls 当负对照）实测：

| 比较的特征 | 答案 | 其中 wrong | 负对照 |
| --- | --- | --- | --- |
| 全部特征（旧做法） | exact 44 / range 43（→ RISC-V），exact 47 / range 36（→ AArch64） | 9、10 | 0 / 1648 |
| 只比字符串（现在，架构不同时自动） | exact 48 / range 12（两个目标相同） | **0、0** | 0 / 1648 |

也就是说"参考库必须同架构"没有以前说的那么绝对：字符串是程序员写的，换 CPU 不变；错误的发行版全部来自编译器派生的常量。代价是答案少了：littlefs 完整保留，zlib 只剩范围，lz4、cJSON、inih、heatshrink 认不出（它们靠常量或可用字符串太少）。对要进 SBOM 的结论，选择"少而不错"。同架构下行为不变。

实现：函数特征现在记录哪些来自字符串；指纹文件升到格式 3，额外记录构建架构和每个函数的字符串个数，旧格式仍可读但没有这两项，所以对旧指纹不会切换到只比字符串。要启用，用 `gangmu rules binary-prints` 重新生成指纹。

## 2026-10-08：调用关系佐证——做了，增益太小，没并入
想法：库里的函数会互相调用，偶然撞上的命中不会；让指纹文件记录函数间调用，命中里有若干条与参考库一致的调用就放宽 `MIN_MATCHES` 与 `MIN_COVERAGE`，以多认出小库。
- 信号本身是真的：放宽到 2 个函数、覆盖率 0.04 后，AArch64 出现 12 次误报（mbedtls 的指纹匹配 zlib 的镜像），这 12 次命中函数之间**一条调用都没有**，而真命中的中位数是十几条一致的调用。
- 但对召回几乎没用：Cortex-M3 无变化，rv32imac 无变化，AArch64 只多 1 个。cJSON、inih、heatshrink 认不出的原因是可指纹的函数只有 1~7 个，函数之间根本没有几条调用，没有东西可佐证。
- 用调用关系区分相邻发行版（打破 `range`）更不行：能转成 exact 的同时，把正确的 range 变成了 wrong（AArch64：19 个转对，21 个转错）；要求大差距则一个也转不了。
所以格式和代码复杂度不值得，放弃。要认出小库，需要的是新的特征类别，而不是更多佐证。


## Xtensa（ESP32）

Capstone 没有 Xtensa 解码器，`src/gangmu/xtensa.py` 只做两件事：按 `entry a1, N`（字节 `36 x1 ..`，4 字节对齐）找函数起点；按 `l32r` 的目标地址读出字面量池里的字（字符串地址和常量都是这样取的）。字面量池本身会被当成指令走一遍，只会多出几个无关特征，包含度匹配能容忍。

语料用 Espressif 官方 `xtensa-esp32-elf-gcc`（`-mlongcalls -mtext-section-literals -ffunction-sections`）交叉编译，由 `benchmarks/binary/build_corpus.py` 的 `xtensa` 目标生成。

| 方向 | 精确 | 区间 | 错 | 认不出 | 负对照 |
|---|---|---|---|---|---|
| Cortex-M3 参考库 → ESP32 镜像（只比字符串） | 48 | 12 | 0 | 212 | 0 / 1648 |
| ESP32 参考库 → Cortex-M3 镜像（只比字符串） | 48 | 0 | 0 | 224 | 0 / 1360 |
| ESP32 → ESP32（全部特征，含 mbedtls） | 114 | 77 | 1 | 128 | 0 / 1920 |

那 1 个错误：zlib v1.3.1，O1 参考库对 Os 镜像，报了 v1.2.11~v1.2.13（区间不含真实版本）。

局限：解码器是手写的，只在一个 gcc 版本上验证；没有真实 ESP-IDF 固件；字符串太少的库（cJSON、inih、lz4、heatshrink）跨架构认不出来，这是只比字符串的固有代价。


## 真实固件（Zephyr 4.1，Cortex-M7）

前面所有数字都来自自己交叉编译的“只含库代码”的镜像。这一节用 Zephyr 4.1 官方示例，经 Zephyr 自己的构建和链接流程（`--gc-sections`、Zephyr 的 mbedtls 配置、`nucleo_h743zi`、arm-none-eabi-gcc 13.2）得到真实固件，去掉符号后用 `gangmu rules` 里已合并的 `.fnprint` 规则扫描。真值取自各固件源码里的版本。

| 固件 | 真值 | 结果 |
|---|---|---|
| `samples/subsys/fs/littlefs` | littlefs 2.10.x（不在指纹覆盖的 10 个版本里） | 认出是 littlefs，但报 **2.0.4**（8/47 个函数，覆盖率 17%）：错 |
| `samples/net/sockets/big_http_download`（TLS，picolibc） | Mbed TLS 3.6.2（Zephyr 分支，在覆盖范围内） | 认出是 Mbed TLS，但报 **2.16.12~3.3.0**（25/124 个函数，覆盖率 20%）：区间不含真值，错 |
| `tests/crypto/mbedtls` | Mbed TLS 3.6.2 | 没认出。这个测试只链进 16 个 mbedtls 函数，几乎没有库代码，算正常漏报 |

结论：
- **库本身（身份）三例里两例认对，另一例几乎没有库代码**；**版本两例都错**。自测里“跨构建全对”只说明方法能区分作者自己编的那几个版本，不能外推到别的配置、厂商分支或不在覆盖集里的版本。
- littlefs 的错是方法固有的：参考集里没有真实版本时，仍然会选出共享函数最多的那个版本。覆盖率不能区分这两种情况：自测里正确答案的覆盖率也只有 0.2 到 0.5（跨优化级别），所以不能靠提高覆盖率门槛来修。
- mbedtls 的错发生在版本**在**覆盖集里的情况，更说明问题：Zephyr 的 3.6.2 和上游 3.6.2 编出来的函数差别大于自测里 -Os 和 -O2 的差别。原因我没有验证，猜测是配置宏和 Zephyr 对库的补丁，尚属推测。
- CPU 型号不是原因：同一份上游 3.6.2 源码用 `-mcpu=cortex-m3/m4/m7` 编出的镜像都能认对（覆盖率 0.75 以上）。

做了什么：覆盖率低于 0.5 时，扫描结果的证据文字里加一句“低覆盖：这个版本只是已指纹化的版本中最接近的，不一定是镜像里的那个”，不改数字。没有改匹配规则，因为样本只有两个固件，不足以据此调阈值。

接下来值得做：多收集几个真实固件（ESP-IDF 需要 Xtensa 的 newlib 和较大的下载，这里没做）；对 Zephyr 分支这类“同版本号不同代码”的情况，要么按 Zephyr 的 mbedtls 分支单独做指纹，要么在规则里标注分支。

### 第二轮：为什么 Mbed TLS 认不对

同一个 TLS 示例换成 `-O2`、换板子（`nucleo_f746zg`）、换应用（`echo_server` 加 TLS），4 个固件都被判成 2.28.0 附近（覆盖率 0.19 到 0.22，区间 `2.16.12~3.3.0` 或更宽），一致地认错。

做了两个实验：
- 用上游 3.6.2 源码，套上 Zephyr 的配置（`config-tls-generic.h`）和 Zephyr 的编译参数重新编译，再用现有指纹匹配：覆盖率 0.21、同样判成 2.28.0。**配置是原因之一。**
- 把这个“Zephyr 配置”的构建作为第三个构建加进 3.5.2、3.6.0、3.6.2 的参考集（其余版本不能用这套配置编译）重新生成：自测出现 1 个答错（3.5.2 的 -O2 参考去认 Zephyr 配置的镜像），没通过，所以没有写入规则。即使强行生成，真实固件的覆盖率仍是 0.19 到 0.22，只是区间变宽到 `2.16.12~3.6.2`，包含真值。**说明除了配置，还有别的差异，没找到。**

结论：给 Mbed TLS 这类配置宏很多的库做指纹，参考构建必须覆盖目标固件会用的配置；只靠一份默认配置的指纹在厂商固件上识别不了版本。是否值得为 Zephyr 的配置单独做一套，取决于有多少用户用 Zephyr。

### 第三轮：根因是打分方式，不只是配置（更正上面两节的原因判断）

按函数名把真实固件和参考构建一一对比后发现：真实 TLS 固件只链进了约 38 个 Mbed TLS 函数（`--gc-sections` 丢掉了其余），这些函数和参考构建里同名函数的特征吻合得很好（37/38 的包含度 ≥ 0.7）。也就是说**函数本身是对得上的，错在版本打分**：原来用 Jaccard（`匹配数 / (该版本函数数 + 匹配数 - 交集)`），固件只含库的一部分时，函数多的新版本分母大、分数低，函数少的旧版本总占便宜，于是 3.6.2 输给了 2.28.0。配置宏确实让匹配数偏少（用上游 3.6.2 源码套 Zephyr 配置编译，匹配数从约 130 降到约 26），但不是选错版本的原因。

修改（`fprint.py`）：版本得分改成“被匹配的函数里，有多少属于这个版本”；能解释全部匹配的版本并列，报成区间；Jaccard 只用来在并列时挑代表。另外要求最佳版本自己至少解释 5 个函数。

对 5 个语料（Cortex-M3、rv32imac、AArch64、Xtensa，Cortex-M3 上的 Mbed TLS 单独一组），同时模拟“只链进一部分”（每个镜像随机只留 25% 的函数）：

| 语料 | 完整镜像：旧 → 新（exact / range / wrong / none） | 只留 25%：旧 → 新 wrong |
|---|---|---|
| Cortex-M3 | 75/62/6/129 → 67/73/1/131 | 14 → 6 |
| rv32imac | 75/109/4/132 → 65/120/3/132 | 3 → 2 |
| AArch64 | 89/106/4/121 → 81/114/4/121 | 10 → 8 |
| Xtensa | 114/77/1/128 → 110/82/0/128 | 4 → 2 |
| Mbed TLS（M3） | 12/36/0/0 → 13/35/0/0 | 2 → 0 |

所有语料的负对照仍然 0 次误报。代价是 exact 少了一些、range 多了一些：镜像含整个库时，新版本包含旧版本的所有函数，现在会报成区间而不是唯一版本。试过要求并列版本的 Jaccard 也接近最佳（θ=0.5、0.7、0.85）来收窄区间，exact 只多一点，部分镜像下 wrong 反而变多，没采用。

真实 Zephyr 固件重测：Mbed TLS 的 4 个固件从“错在 2.28.0 附近”变成 `2.16.12~3.6.2`（最佳 3.5.2），**区间包含真值 3.6.2，但很宽**；littlefs 示例（真值 2.10.x，不在指纹覆盖的 10 个版本里）变成 `2.1.0~2.2.1`，**仍然错**，这是方法固有的：参考集里没有的版本无法识别。

Mbed TLS 规则的指纹需要用新打分重新生成（自测数字从 exact 1 / range 17 变成 exact 0 / range 18）；littlefs 的 sha256 和自测数字没变。

## 第四轮：参考构建里的 assert 让 littlefs 在真实固件上失效

又编了 Zephyr 3.7.0（littlefs 2.8.1、Mbed TLS 3.6.0）和 4.0.0（littlefs 2.9.3、Mbed TLS 3.6.2）的 littlefs 示例和 TLS 示例，连同 4.1 共 3 个 littlefs 固件和 3 个 TLS 固件，用已合并的规则扫描。身份 6/6 认对。版本：

- **Mbed TLS**：3 个都报 `2.16.12~3.6.2`（包含真值，但很宽），与前面一致。
- **littlefs：3 个都错**——2.8.1 和 2.9.3 虽然在指纹覆盖的版本里，也被报成 `2.1.0~2.2.1`（4.1 的 2.10.x 报成 `2.0.4`）。

按函数名对比发现，真实固件里 `lfs_init` 等函数提取到的特征是 0 个，而参考构建里有 21 个。原因是参考构建**带着 `assert()`**：每个 assert 把表达式文本（如 `lfs->cfg->block_size >= 128`）、文件名和行号留在镜像里，littlefs 的 467 个有指纹的函数大部分靠这些特征撑起来。出货的固件几乎都关了 assert，所以这些特征在真实镜像里不存在，自测却看不出来，因为参考和自测镜像都是同一种构建。

修改：`build_corpus.py` 默认加 `-DNDEBUG -DLFS_NO_ASSERT`（`--asserts` 保留旧行为）。用这样编出的参考重新生成 littlefs 指纹：

| | 旧（带 assert） | 新（无 assert） |
|---|---|---|
| 有指纹的函数 | 467 | 102 |
| 自测跨构建 | 20 exact | 16 range（0 错，0 认不出） |
| 能进规则的版本 | 10 个 | 8 个（1.7.2 没有可用特征，2.2.1 在 -Os/-O2 之间会答错） |
| Zephyr 3.7.0（真值 2.8.1） | `2.1.0~2.2.1`，错 | `2.6.1~2.9.3`，包含真值 |
| Zephyr 4.0.0（真值 2.9.3） | `2.1.0~2.2.1`，错 | `2.6.1~2.9.3`，包含真值 |
| Zephyr 4.1（真值 2.10.x，不在覆盖集） | `2.0.4`，错 | `2.6.1~2.9.3`，上界 2.9.3 是覆盖集里最新的，不含真值 |

自测通过的指纹数从 467 掉到 102，说明“自测全对”曾经依赖不真实的特征。这个教训适用于所有库：参考构建必须和出货构建一样关掉 assert、日志等调试输出。只重测了 littlefs 和 Mbed TLS（后者指纹数不变，仍是 447，没有 assert）；zlib、lz4、cJSON 等其他库和前面几组基准数字没有用无 assert 的构建重测，可能有同样的问题。


## 第五轮：全部基准改用无 assert 的构建重测

第四轮发现带 `assert()` 的参考构建会让 littlefs 的指纹虚高。为了知道前面各节的基准数字有多少受影响，把四种架构的语料全部用无 assert 的构建（`build_corpus.py` 的新默认）重编，`gangmu binary-eval` 重测。同时 Mbed TLS 现在也在这几个语料里（原来 Cortex-M3 那组没有）。

| 架构 | 旧（带 assert，exact / range / wrong / none） | 新（无 assert） | 其中 littlefs 旧 → 新 |
|---|---|---|---|
| Cortex-M3 | 67 / 73 / 1 / 131（无 Mbed TLS） | 51 / 131 / 7 / 131 | 42/6/0/0 → 13/29/6/0 |
| rv32imac | 65 / 120 / 3 / 132 | 18 / 158 / 12 / 132 | 48/0/0/0 → 1/38/9/0 |
| AArch64 | 81 / 114 / 4 / 121 | 34 / 161 / 4 / 121 | 48/0/0/0 → 2/45/1/0 |
| Xtensa | 110 / 82 / 0 / 128 | 39 / 150 / 3 / 128 | 48/0/0/0 → 7/40/1/0 |

只有 littlefs 的数字明显变化（assert 字符串曾经让它几乎每个版本都能唯一识别，现在多数只能给区间，rv32imac 上还有 9 个答错）；zlib、lz4、cJSON、inih、heatshrink 在 Cortex-M3 上的结果与旧的完全相同。负对照在四个语料上仍是 0 次误报。

跨架构（只比字符串）重测：Cortex-M3 参考库对 rv32imac、AArch64、Xtensa 镜像各给出 57、60、57 个答案，0 个错误；Xtensa 参考库对 Cortex-M3 镜像 48 个答案，0 个错误；负对照 0 次误报。此前“另有 48 个 littlefs 精确命中”的说法来自 assert 字符串，不再成立。

结论：前面各节里 littlefs 的精确命中数是在带 assert 的构建上测的，偏乐观；其他库的数字不受影响。基准语料和 `.fnprint` 一样，必须按出货构建（关 assert、关调试输出）来编。

## 版本评分改为按「矛盾证据」计（2026-10）

之前给版本打分用「这个版本解释了多少匹配上的函数」的占比，占比在最优的 85% 以内的版本一起报成区间。两处不合理：
一是 20 个匹配里的第 3 个矛盾和 200 个里的第 30 个同样算 15%；二是只有 2 个特征的指纹是许多无关函数的子集，
偶然命中一条就被当成一条完整的反证，把真实版本挤出区间（littlefs 的 v2.4.0 被报成 v2.5.0 就是这样）。

现在每个匹配上的指纹，如果该版本不含它，就记一次矛盾，权重按特征数：4 个及以上算 1，2 个算 1/3；
与最优版本相差不超过 2 个权重的版本一起报成区间。特征数 4 取自「少于 4 个特征的指纹偶然命中很常见」；间隔 2 是我对照下表三个语料选的：
选的是三者的错误都不超过 2 的最小间隔，不是任何单个语料上的最优点（只看 Cortex-M3 会选间隔 1 以外的别的值）。
下表同时给出相邻取值，趋势是平滑单调的（间隔越大，错误越少、唯一识别越少），不是一个刀口上的点：

| 语料（参考 → 镜像） | 旧：解释占比 0.85 | 新：矛盾，间隔 1 | **新：矛盾，间隔 2（默认）** | 新：矛盾，间隔 3 |
|---|---|---|---|---|
| Cortex-M3 → Cortex-M3 | 52 / 130 / **7** / 131 | 54 / 128 / 7 / 131 | 35 / 153 / **1** / 131 | 24 / 165 / 0 / 131 |
| AArch64 → AArch64 | 34 / 161 / **4** / 121 | 73 / 117 / 8 / 122 | 47 / 149 / **2** / 122 | 26 / 170 / 2 / 122 |
| Cortex-M3 → AArch64（只比字符串） | 22 / 102 / **7** / 189 | 31 / 94 / 6 / 189 | 19 / 112 / **0** / 189 | 18 / 113 / 0 / 189 |

每格依次是 exact / range / wrong / none；三个语料的负对照都是 1920 对 0 次误报。
默认取间隔 2：三个语料里错误都降到 2 个以内（共 18 个降到 3 个），代价是 Cortex-M3 上唯一识别的少了 17 个，
AArch64 上反而多了 13 个，多出来的更多变成了区间。**这是用宽一点的区间换更少的错误**，和这个工具对「错报版本比报区间更糟」的取舍一致。

局限：
- 只在自己交叉编译的两个架构、7 个库上测过；**没有用真实固件复测**（Zephyr 那组需要原始构建，这次没有重跑）。
- 剩下的错误里，`-O0` 构建的参考库去识别 `-Os`/`-O2` 的镜像仍是主要来源（lz4），原因没变：`-O0` 里没有内联，
  大函数的特征和优化后的镜像差得远。
- 旧的评分仍可用：`gangmu binary-eval --tie-share 0.85`；规则文件里已记录的自测结果不受影响，
  它们是写进旁路文件里的，不随评分方式重算。


## Windows PE（`.exe`/`.dll`，含 Windows CE 的支持范围）（2026-10）

函数指纹原来只读 ELF 和 Cortex-M `.bin`；现在也读 PE（x86、x64、ARM、Thumb、ARM64；Windows CE 靠子系统 9 识别，
SH/MIPS/PowerPC 没有解码器，结果里写「不支持」）。x64 的函数边界取自异常表，其余靠扫描。

**真实二进制（只有这两个，都是 x64、MinGW 构建，官方发布包里的 `lz4.exe` 和 `zstd.exe`）。** 参考库用本机 Linux gcc 编译成
ELF（`-Os`/`-O2`/`-O1`），所以编译器、系统和文件格式都和镜像不同，这是规则作者实际会遇到的情形。真值来自发布包的版本号。

| 镜像（真值） | 参考 | 报告 | 真值是否在答案里 | 命中/全部 |
|---|---|---|---|---|
| lz4.exe（1.9.4） | -Os | 1.10.0，区间 1.9.4~1.10.0 | 在区间内 | 37/40 |
| | -O2 | 1.10.0 | **不在（差一个版本）** | 38/39 |
| | -O1 | 1.10.0，区间 1.9.4~1.10.0 | 在区间内 | 37/39 |
| zstd.exe（1.5.5） | -Os | 1.5.4，区间 1.5.2~1.5.6 | 在区间内 | 25/40 |
| | -O2 | 1.5.5，区间 1.5.4~1.5.5 | 在 | 32/50 |
| | -O1 | 1.5.4，区间 1.5.4~1.5.5 | 在区间内 | 32/45 |

6 个答案里 5 个的区间包含真值，1 个错一个相邻版本（lz4 -O2）。原因：参考和镜像来自不同编译器，同一个函数的常量集合略有
差别，几个函数在相邻版本的指纹上匹配得不一样；矛盾分之差（3）超过区间宽度 2，所以没有并入区间。这里没有调整任何参数去迎合它。

**不是误报：两个库共享同一份第三方代码。** 把 zstd 的参考拿去匹配 lz4.exe（177 个函数）、把 lz4 的参考拿去匹配
zstd.exe（564 个函数），都得到答案：覆盖率 0.15 到 0.33，命中 7 到 11 个函数（真实命中是 35 到 59 个、覆盖率 0.62 到 0.97）。
（本节上一版把这些归因于小指纹偶然命中，这个判断是错的，已更正。）逐个对照参考构建的符号名，命中的函数全是
xxHash：zstd 参考里的 `XXH32_finalize`、`XXH64`、`ZSTD_XXH64_update` 等 8 个，lz4 参考里的 `XXH32`、`XXH64_digest` 等 7 个。
lz4 和 zstd 都带着 xxHash，所以这是真的命中，只是命中的是 xxHash，不是 zstd 或 lz4 本身。

对产品的含义：一个库的指纹里如果含有别的库也带的代码（xxHash、zlib 的小片段、常见的哈希和压缩例程），而镜像只包含那一段，
就会被报成这个库，覆盖率偏低（这里 0.15 到 0.33）。小库的负对照里镜像只有一个库，看不到这一点；规则作者只有在
`--negative` 里给出带同样代码的镜像时才会发现。生成指纹时可以用 `--negative` 给出带同样代码的镜像，共享的函数会被自动剔除（见下）。
没有直接提高覆盖率下限，因为 0.33 和跨架构只比字符串时的真阳性（0.12 到 0.3）重叠。

### 剔除与其他程序共享的函数

`gangmu rules binary-prints --negative` 给出的镜像里已经含有的参考函数，会从指纹和自测里去掉（`fprint.split_shared`，
匹配规则和识别时相同）。超过参考函数的一半被剔除时认为负对照就是库本身，不剔除。

验证：x86-64 参考（lz4 v1.9.2 到 v1.10.0、zstd v1.5.2 到 v1.5.6，各 -Os/-O2/-O1），负对照是单独编译的 `xxhash.c`
（-Os、-O2），被测的是官方 `lz4.exe`、`zstd.exe`。6 个组合里，对方 exe 上的命中 6 个全部消失；自己 exe 上的答案不变
（lz4 都是 1.10.0 或 1.9.4~1.10.0，zstd 为 1.5.4、1.5.5 及其区间，与剔除前相同），覆盖率下降 0.01 到 0.11。只验证了
这一对库。负对照里只有 xxHash 一类共享代码；别的共享代码（zlib 片段、常见哈希）要规则作者给出对应的镜像才会剔除。

## MIPS32（小端和大端）（2026-10）

函数指纹原来不认 MIPS 的 ELF。现在支持 MIPS32：边界靠 `jal` 目标、`addiu $sp,$sp,-N` 序言和 `jr $ra`（分支延迟槽里的
一条指令仍属于该函数），特征靠 `lui`+`addiu`/`ori` 还原常量和字符串地址；位置无关代码按 `$gp = _gp_disp + $t9` 取 GOT 项，
`_gp_disp` 不算常量。

**语料：** `build_corpus.py --target mipsel` / `--target mips`，用 clang+lld 交叉编译（本机没有 MIPS GCC；`-fno-pic
-mno-abicalls -G0`），库的头文件用 `benchmarks/binary/mips-include/` 里的最小桩。能编译的有 lz4（3 个版本）、littlefs
（3 个版本）、heatshrink（2 个版本），各 `-Os/-O2/-O1/-O0`。

| 字节序 | 精确 | 区间 | 错 | 认不出 | 负对照误报 |
|---|---|---|---|---|---|
| 小端 | 23 | 71 | 2 | 32 | 0/256 |
| 大端 | 23 | 72 | 1 | 32 | 0/256 |

错的 3 个都是 littlefs：用 `-O1`/`-O2` 的参考去识别 `-O0` 的镜像（`-O0` 与优化后的代码相差大，ARM 语料里也是主要错误来源，方向相反）。认不出的 32 个全是 heatshrink，
和 Cortex-M3 语料一样：指纹函数太少。

**函数边界（剥离符号的 ELF 对照符号表）：** 小端 3306 个命中、0 个漏、36 个多出（精确率 0.989，召回率 1.000）；大端 3309/0/38。
多出的 33 个在 `-O0` 构建里，其余优化级别每个镜像 1 到 3 个。这是静态链接、只有库代码的合成镜像，不代表真实固件。

**这些数字的来历（避免过拟合）：** 解码器先对着 lz4 调出来（边界 151/151），littlefs 和 heatshrink 是之后才测的，没有为它们改过东西。
位置无关代码的 `$gp` 处理是看了一个 PIC 小样例之后加的，只有那个样例和一个单元测试覆盖，没有 PIC 的大语料。

**没做的：** 真实 MIPS 固件（没有样本）；MIPS64、microMIPS、MIPS16；用 gcc 编译的 MIPS（固件常用）；Cortex-M 参考对 MIPS 镜像按
字符串比较（这三个库几乎没有字符串，测不了）。

### 真实 MIPS 库：OpenWrt 的大端 mips_24kc 包（2026-10）

下载的是 OpenWrt 官方包（downloads.openwrt.org，不入库），版本由包名确定，都是 gcc+musl 编译的位置无关共享库、大端。

* **libmbedcrypto 2.28.10**（OpenWrt 23.05.5，普通 MIPS32）：用 clang 非 PIC 编译的 mbedtls 参考（v2.28.0、v2.28.8、v3.6.0，`-Os`/`-O2`）识别，
  答案是区间 `v2.28.0~v2.28.8`，96 个指纹函数里命中 61（`-Os`）和 58（`-O2`）。真实版本 2.28.10 不在参考里，最近的参考 2.28.8 在区间内，
  没有错报成 3.x。**只有这一例**，参考和目标的编译器、PIC 与否、优化级别都不同。
* 这次暴露了两个问题，已修：OpenWrt 把共享库的节表剥掉了（只剩程序头），此前读不出任何函数，现在由 `PT_LOAD` 段合成节，并从

**同一个库、参考里加入真实版本后（2026-10-16）：** 参考换成 v2.28.0、v2.28.3、v2.28.5、v2.28.8、v2.28.10、v3.6.0。`-O2` 参考答案是精确的 `v2.28.10`（59/105）；`-Os` 参考最佳是 `v2.28.8`（61/96），区间 `v2.28.0~v2.28.10` 含真实版本。2.28.x 各版之间代码几乎相同，所以区间很宽，这是预期的。仍只有这一个库。

`LC_FUNCTION_STARTS`。后者是链接器写进去的每个函数起点列表，剥了符号也在，作用相当于 x64 PE 的 `.pdata`：边界是精确的，不用扫描估计。
支持 x86、x86-64、ARM64；32 位 ARM 的 Mach-O 和大端（PowerPC）明确报「不支持」。模块：`macho.py`、`disasm.recover_macho`、`fprint.memory_from_macho`。

### Windows on ARM64 的 PE（2026-10）

ARM64 的 PE 也有 `.pdata`，每项 8 字节：起始 RVA 和展开信息。展开信息低两位非 0 是压缩格式（函数长度在第 2 到 12 位，单位字，即乘 4 字节），否则是 `.xdata` 记录的 RVA，
记录第一个字的低 18 位是函数长度（字）。以前 ARM64 的 PE 只靠扫描。现在和 x64 一样用这张表给出精确起止，扫描补齐表里没有的函数。

**真实样本：** PyPI 的 `zstandard` 0.25.0 `win_arm64` wheel（`backend_c.cp312-win_arm64.pyd`，静态链接 zstd 1.5.7）。表里列出 803 个函数；只用扫描时，
这 803 个起点只找到 345 个（43%），另多出 271 个表里没有的起点（可能是无展开信息的叶子函数，没逐个核对）。识别结果：对 gcc 的 Linux aarch64 参考（zstd 1.5.2 到 1.5.7），
`-Os` 和 `-O2` 都答出 v1.5.7，与真实版本一致，命中 35/126 和 30/143；改前是 36/126 和 31/143，答案没变。所以这次改动提高的是函数边界，不是识别率。只有这一个样本，
只有 0.25.0 有 win_arm64 的 wheel，没有 0.23.0 可对照。

## 跨架构：只报库，版本给整个区间（2026-10-17）

镜像和指纹不是同一种 CPU 时，引擎只比较字符串（常量随编译器和架构变化）。用 Cortex-M 的 Mbed TLS 指纹扫 rv32imac 的 mbedtls 镜像，字符串匹配会给出单一的错版本：
2.28.2 的镜像报成 3.1.0（可信度 0.60），3.6.5 报成 3.5.2~3.6.2（真值在区间之外）。所以现在这种情况下只报库，版本写成该规则记录的整个区间（`最早~最晚`），
证据里写明「版本没有收窄，列出了规则覆盖的所有版本」和「只比较了字符串」；规则只有一个版本时不受影响。同架构的指纹仍给出单一版本或匹配区间。
这样跨架构的结果更不精确，但不再给出错误的单一答案；要收窄版本，规则里需要镜像所在架构的指纹（见 gangmu-rules）。

**最新版本提示（2026-10-17）：** 答案落在指纹所含的最新发布版（或区间上端就是它）时，证据里加一句「X 是指纹里最新的发布版，镜像可能是更新、指纹没有覆盖的版本」。
原因：指纹里没有的更新版本会被归到最近的区间，区间不含真值。例如 RISC-V 的 mbedtls 指纹最新到 3.6.2，3.6.5 的镜像报 `3.6.0~3.6.2`（命中 115/125），真值在区间之外；
littlefs 指纹最新到 2.9.3 时，2.10.2 和 2.11.0 的镜像都报 `2.0.4~2.9.3`。引擎无法判断是否真有更新版，所以只提示，不改答案。

## clang 编译的 Thumb 固件与 Linux 用户态库（2026-10-18）

* clang 编译的 zlib（Cortex-M3）函数边界：召回 0.98，精确率 0.60–0.65。多出来的是函数内部被切开（如 `adler32_z`），漏掉的是被尾调用的叶子函数（`crc32_z`）。
* 能不能识别：见本节最后的「编译器换了会怎样」，当时用了 `Z_SOLO`、无法判断，后来补了对照实验。
* 修复的静默失败：无入口点的 ELF 被当成 ARM 模式；向量表不在偏移 0 的镜像（应用基址 0x08008000、MCUboot 头）被报 unknown。修复后 11/11 函数恢复。
* Ubuntu 24.04 的 13 个库：改前 0/13，改后 4/13（expat 2.6.1、libjpeg-turbo 2.1.5、Lua 5.4.6 来自横幅，libzstd 来自 `.note.package`）。清单开销约 0.07 秒/MB。
* 更正：Ubuntu 的 `libz.so.1` 没有 `inflate 1.3 Copyright` 横幅，之前的说法有误。

### 函数边界精确率修复（2026-10-18）

上面 0.60–0.65 的精确率几乎全部来自一个原因：`adler32_z` 里的 26 个假起点。`.rodata` 里 zlib 的固定哈夫曼表恰好有一些形如 `0x080000xx` 的字，重复出现就被「指针被引用两次」的规则收下。修复后（只数代码字面量池里的重复指针），6 个 clang 构建（O1/O2/Os，裸镜像与 ELF）的结果：召回仍是漏掉 `crc32_z` 一个，假起点 26–28 个降到 1–3 个，精确率约 0.98。剩下的假起点落在 `crc32_z` 内部。仍只在 clang 编译的 zlib 一个库上量过，不代表其他代码。

### 编译器换了会怎样：gcc 参考指纹对 clang 构建（2026-10-18）

之前的 clang 构建用了 `Z_SOLO`，与规则里 gcc 参考构建的配置不同，没法判断识别不出（或识别出）是不是编译器造成的。这次装了 `arm-none-eabi-gcc 13.2.1`，用同一份 `benchmarks/binary/build_corpus.py` 与同一份 `libs.yaml`（同样的源文件、同样的启动代码和桩 libc、`-mcpu=cortex-m3 -mthumb`、`-Os` 与 `-O2`），只换编译器：新增目标 `--target arm-clang`（`clang --target=thumbv7m-none-eabi`，仍由 GNU 驱动链接）。去符号后用 `gangmu-rules` 里已发布的 `.fnprint` 识别；zlib 的镜像还把 `deflate/inflate X.Y.Z Copyright` 横幅改写成等长的 `x`，否则版本是从横幅读到的，不是函数指纹。

| 库 | gcc 构建（参考同源，同编译器） | clang 构建 |
|---|---|---|
| zlib（1.2.11 / 1.2.13 / 1.3.1 × Os/O2，6 个镜像） | 6/6 识别，覆盖 65–85%，区间含真值 | 6/6 识别，覆盖 26–27%，区间含真值 |
| Mbed TLS（2.28.0 / 2.28.8 / 3.6.0 × Os/O2，6 个镜像） | 6/6 识别，覆盖 78–94% | 6/6 识别，覆盖 29–33% |
| littlefs（2.4.0 / 2.5.0 / 2.9.0 × Os/O2，6 个镜像） | 6/6 识别，覆盖 56–85% | **0/6，识别不出** |

* 换编译器后，覆盖率从 56–94% 降到 26–33%，仍在 `MIN_COVERAGE`（12%）之上，所以能认出库；但每次都会触发已有的「低覆盖」提示（覆盖低于 50%）：版本只是最近的一个。
* 版本不可靠：12 个 clang 构建里，Mbed TLS 2.28.0 的 `-O2` 报成 `3.1.0`，区间不含真值。其余 11 个区间含真值，但 Mbed TLS 的区间很宽（例如 `2.28.0~3.5.2`）。clang 构建里每个发行版都缺约 54 个已匹配的指纹，发行版之间的差距落在噪声里。
* 对照：gcc 的 littlefs 2.4.0、2.5.0 报 `2.6.1~2.9.3`，区间不含真值——参考指纹里没有这两个发行版，与编译器无关，是已知的「参考没覆盖的发行版」。
* 假阳性：clang 构建的 cJSON 和 littlefs 共 12 个镜像，没有一个被报成 zlib。
* 结论：换成 clang，库还能认出来（zlib、Mbed TLS）或认不出来（littlefs），版本要看区间，别看单个版本号。规则的参考指纹只用 gcc 构建，要让 clang 构建也可靠，参考得加 clang 构建，这需要重新生成 `.fnprint` 并走校准。

### 试过没采用：把 `.rodata` 里的常量表当特征

想法：CRC 表、哈夫曼表的字节在 gcc 与 clang 构建里完全一样，不随编译器变化，可作为新的一类特征。试验：在 `function_features` 里，函数引用只读数据中的地址（不是字符串）时，取该地址起 32 字节做一个哈夫曼式的哈希特征，用 gcc 构建生成参考，再认 clang 构建。结果：没有改善，反而更糟。原因是这些固件把 `.rodata` 放在 `.text` 里（嵌入式的常见链接脚本），无法可靠地区分「常量表」与「函数内部的地址」：把函数起点排除后，参考指纹里的特征数量翻了几倍，全是构建特有的噪声，三个库 18 个镜像一个也认不出。没有可靠的代码/数据分界就做不好这件事，所以没有采用，代码已撤回。

### 试过没采用：给参考指纹加上 clang 构建（2026-10-18）

动机：上面 clang 构建只认出库、版本区间宽。想法是在参考里同时放 gcc 和 clang 的构建，让 clang 编译的固件（Keil 的 Arm Compiler 6 基于 LLVM，国内很常见）也有同编译器的参考。

做法：zlib 的 7 个发行版（1.2.8、1.2.11、1.2.12、1.2.13、1.3、1.3.1、1.3.2）各用 gcc 和 clang 编 `-Os`、`-O2`（`build_corpus.py` 新增 `--tag`，用来指定发行版），每个发行版 4 个构建。

* **现有的自检过不了。** `gangmu rules binary-prints` 的自检把每个构建单独当参考，去认其他构建的镜像。gcc 与 clang 混合的配对几乎都认不出：84 个跨构建配对里 55 个认不出来，自检判为不通过，规则不能带这样的指纹。只用 gcc 构建时本机复现的结果是 13 个区间、1 个认不出（已发布的指纹是 14 个区间、0 个认不出，构建参数略有不同）。
* **换成更合理的测法也不行。** 把被测的 clang 构建拿掉，用其余所有构建（含同一发行版的另一个 clang 优化级别）合成参考，再认这个镜像（zlib，14 个 clang 镜像）：
  * 只有 gcc 参考：覆盖 24–29%，区间都宽，且都含真值。
  * gcc + clang 参考：覆盖升到 40–52%，但区间变窄后常常不含真值：1.2.12 的镜像报 `1.3~1.3.2`，1.2.8 的镜像报 `1.2.11`，1.2.11 的 `-O2` 报 `1.2.8`，1.3.1 的 `-Os` 报 `1.3~1.3.2` 等，14 个里 11 个不含真值。
* 原因：zlib 相邻发行版的代码只差几个函数，clang 与 gcc 的差别（寄存器分配、常量折叠）比发行版之间的差别大。覆盖率提高了，区分发行版的能力没有同步提高，反而给出了看上去更确定的错误答案。
* 结论：不加 clang 参考。对 clang 构建，宽区间加低覆盖提示才是诚实的答案。要让 clang 构建能分辨发行版，需要的是对不同编译器稳定的特征，而不是更多参考构建；常量表的试验也没成功（见上一节）。这个方向暂时没有可行做法。

## x86-64 函数指纹：zlib、littlefs、Mbed TLS（2026-10-19）

之前免费库里的函数指纹只有 Thumb（和 RISC-V），x86-64 的 ELF 库和 Windows 的 PE 没有参考可比。这次补上：`build_corpus.py --target x86-64`（原生 GCC 13、`-ffreestanding -fno-pic -fno-pie -fno-stack-protector -fcf-protection=none`、只含库自己的代码，和其他架构一样），按已有指纹相同的发行版构建，用 `gangmu rules binary-prints` 生成并自检，发布在 gangmu-rules 的 `<库>.x86-64.fnprint`。

| 库 | 发行版 | 指纹函数 | 构建 | 自检（跨构建） |
|---|---|---|---|---|
| zlib | 7（1.2.8–1.3.2） | 25 | -O2、-O3 | 区间 14，错 0，认不出 0 |
| littlefs | 10（2.0.4–2.11.0） | 59 | -Os、-O2 | 区间 20，错 0，认不出 0 |
| Mbed TLS | 11（2.16.12–3.6.5） | 225 | -O2、-O3 | exact 4，区间 18，错 0，认不出 0 |

负对照（其他库的 x86-64 构建）都是 0 次误报。**优化级别是按库挑的，能过自检的那一对**：zlib 带 -Os 的三种组合各有 1 个镜像认不出，Mbed TLS 的 -Os/-O2、-Os/-O3、-O1/-O2、-O1/-O3 各有 1–2 个错误答案，littlefs 的 -O2/-O3 有 2 个错误答案，这些组合没有采用。这是对自己构建的自检，不能保证别的编译参数也过。

**在参考没见过的构建上的验证**（Mbed TLS，真值都是 2.28.8）：

| 镜像 | 结果 |
|---|---|
| Ubuntu 24.04 的 `libmbedcrypto.so.2.28.8`（发行版编译参数，版本横幅抹掉） | `2.28.0~3.3.0`，80%（90/112）；修复立即数的误判之前是 79%（89/112） |
| 同一份源码用 mingw-w64 `-O2` 编成 PE（去符号，gangmu 0.13.0 的 `scan`） | `2.28.0~2.28.8`，88%（99/112） |
| Ubuntu 的 `libmbedtls.so`、`libmbedx509.so` | 认不出：参考里没有 ssl、x509 的代码（`libs.yaml` 排除了它们） |

两个区间都含真值，但单个最佳版本不准（报成 2.28.2、2.28.4），要看区间，不要看单个版本。

**zlib 在 x86-64 上认不出 Ubuntu 的 `libz.so.1.3`，原因在特征提取，不在参考太少**（见下一节）。zlib 自己的指纹函数确实不多（25 个带至少 2 个特征，x86 的特征只有立即数和 RIP 相对的字符串）。littlefs 没有发行版里的构建可测，只有自检的数字。

复现：`build_corpus.py --target x86-64 --lib <库> --tag … --opt O2 --opt O3`，再用 `gangmu rules binary-prints --ref 发行版:构建=PATH …`；负对照用 cjson、lz4、heatshrink、inih 和另外两个库的 x86-64 构建。
